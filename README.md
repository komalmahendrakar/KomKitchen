# Live Kitchen Operations — Full-Stack Real-Time Food Ordering System

A production-grade, highly reliable food-ordering and kitchen operations platform built for high-concurrency environments.

Built with **PostgreSQL**, **Node.js / Express**, **TypeScript**, **Socket.IO**, and **React + Vite**.

---

## 📌 Architecture & Design Highlights

### 1. Non-Negotiable Inventory Correctness (PostgreSQL ACID Transactions)
- **Problem**: In high-traffic scenarios, standard read-then-write patterns (`SELECT stock ... if stock > 0 ... UPDATE stock`) result in overselling due to race conditions.
- **Solution**: All inventory deductions are executed using atomic conditional updates within an explicit transaction on a single checked-out database client:
  ```sql
  UPDATE menu_items
  SET stock = stock - $1,
      updated_at = CURRENT_TIMESTAMP
  WHERE id = $2 AND stock >= $1
  RETURNING id, name, price, stock;
  ```
- If any requested line item fails this condition (meaning available stock < requested quantity), the entire transaction is rolled back with an immediate `ROLLBACK` command.
- Zero partial reservations: The customer either reserves every item or nothing.
- The connection is strictly released in a `finally` block:
  ```typescript
  export async function withTransaction<T>(
    callback: (client: pg.PoolClient) => Promise<T>
  ): Promise<T> {
    const client = await pool.connect();
    try {
      await client.query('BEGIN');
      const result = await callback(client);
      await client.query('COMMIT');
      return result;
    } catch (error) {
      await client.query('ROLLBACK');
      throw error;
    } finally {
      client.release();
    }
  }
  ```

### 2. Strict Idempotency with `clientRequestId`
- Every order payload requires a unique `clientRequestId` generated by the frontend.
- Backed by a unique database constraint (`UNIQUE (client_request_id)`).
- When a client retries or experiences network interruptions, the transaction detects the existing `client_request_id` and safely returns the committed order without double-charging or deducting inventory twice.

### 3. Kitchen State Machine & Optimistic Concurrency
- Validated state flow: `NEW` ➔ `COOKING` ➔ `READY` ➔ `PICKED_UP`.
- Concurrent update safety: Conditional updates require both `orderId` and `expectedCurrentStatus`:
  ```sql
  UPDATE orders
  SET status = $1, updated_at = CURRENT_TIMESTAMP
  WHERE id = $2 AND status = $3
  RETURNING ...;
  ```
- If another kitchen operator already transitioned the ticket, 0 rows are affected and the server returns a `409 Conflict (STATUS_CONFLICT)` with the current active status, preventing stale overrides.

### 4. Real-Time Synchronization & Monotonic Sequencing
- REST handles transactional state changes and authoritative snapshot retrieval.
- Socket.IO broadcasts events **only after transaction commits**:
  - `STOCK_UPDATED` (broadcasted to all customer menus)
  - `ORDER_CREATED` (broadcasted to kitchen terminals)
  - `ORDER_STATUS_CHANGED` (broadcasted to kitchen and individual order channels)
- A dedicated `sequence_tracker` table in PostgreSQL generates a strictly monotonic sequence counter (`sequenceNumber`) for every state-changing event. Clients verify continuity and trigger authoritative snapshot resynchronization on sequence gaps or network reconnects.

## 🚀 Setup & Installation

### 1. Database Configuration
Ensure PostgreSQL is running locally on port `5432`. Create the database:
```sql
CREATE DATABASE kom_kitchen_db;
```

Configure your environment file `server/.env`:
```env
PORT=4000
NODE_ENV=development

PGHOST=localhost
PGPORT=5432
PGDATABASE=kom_kitchen_db
PGUSER=postgres
PGPASSWORD=your_actual_password

CLIENT_URL=http://localhost:5173
```

### 2. Run Database Migrations & Seeds
From the root directory:
```bash
# Run versioned migrations
npm run migrate --workspace=server

# Seed menu items (including the limited-stock item with stock = 1)
npm run seed --workspace=server
```

### 3. Start Development Servers
Run both backend and frontend:
```bash
# Terminal 1: Backend API & Socket Gateway
npm run dev:server

# Terminal 2: Customer & Kitchen Frontend
npm run dev:client
```
- Customer Menu: [http://localhost:5173](http://localhost:5173)
- Kitchen Board: [http://localhost:5173/kitchen](http://localhost:5173/kitchen)

## 🎥 Demonstration Video Walkthrough Guide

To record the required two-customer, one-last-item demonstration:

1. **Setup**:
   - Open two side-by-side browser windows:
     - **Window A**: Customer 1 (`http://localhost:5173`)
     - **Window B**: Customer 2 (`http://localhost:5173`)
     - **Window C**: Kitchen Screen (`http://localhost:5173/kitchen`)
2. **Observe Seeded Stock**:
   - Locate the **"Artisan Wagyu Cheeseburger"** with badge **"ONLY 1 LEFT!"**.
3. **Simultaneous Checkout**:
   - Add the Wagyu Cheeseburger to both carts.
   - Click **Place Order** on both windows in rapid succession.
4. **Expected Behavior**:
   - Customer 1 succeeds (201 Created), redirects to the Order Tracking page showing status `NEW`.
   - Customer 2 is immediately rejected with a clean `409 Conflict: Insufficient stock for Artisan Wagyu Cheeseburger`.
   - The Wagyu Cheeseburger badge immediately updates across all screens to **"OUT OF STOCK"** via Socket.IO without page reload.
5. **Kitchen Workflow**:
   - On the Kitchen Board, observe Customer 1's order appear in **"Incoming Orders"**.
   - Click **"Start Cooking"** ➔ Watch status change to `COOKING` on both the kitchen screen and Customer 1's tracking progress bar.
   - Click **"Mark Ready"** ➔ Watch status change to `READY`.
   - Click **"Complete Picked Up"** ➔ Watch status change to `PICKED_UP`.
